# Weighing a source

Roughly, in descending order of trust:

1. **Primary documentation** — the project's own docs, API reference, or repo.
   Correct for how something is *supposed* to work.
2. **Source code and issue trackers** — correct for how it *actually* works.
   A closed issue often beats the docs.
3. **Release notes and changelogs** — the best source for "when did this change".
4. **Reputable technical writing** — a named author with demonstrable expertise.
5. **Aggregator blog posts** — often SEO restatements of a primary source.
   Follow the citation and read that instead.
6. **Marketing pages** — accurate about features, unreliable about limitations.
   Note what they omit.

## Specific traps

**Benchmark numbers** are almost always self-reported by the party that benefits.
Say who produced them.

**"Best X in 2026" listicles** are usually affiliate content. Treat them as a
list of candidates to verify, never as an evaluation.

**Stack Overflow answers** carry a date. A highly-upvoted answer from 2019 may
describe an API that no longer exists.

**LLM-generated content** now saturates search results for technical topics. Signs:
confident prose with no specific version numbers, no code that could be run, and
a suspiciously even structure. Prefer sources with concrete, checkable detail.
